Contributing

Contributions are welcome! This page summarizes the conventions that new functions should follow, such that they work well with the rest of the package. Following them makes the review of a pull request much faster.

Interface

Inputs are atoms

Functions that operate on structures receive the atoms, as an AbstractVector{<:Atom}. This accepts the result of read_pdb (a Structure), selections, residues, chains, and any other vector of atoms. Do not accept file names or selection strings: reading and selecting are done before, with the functions of the package:

atoms = read_pdb("file.pdb", "protein and chain A")   # reading and selecting
result = new_function(atoms)                           # the new function receives atoms

Name the argument atoms, as in the rest of the package.

Reuse the functions of the package

Before writing a helper function, check if the package already provides it. For example:

  • per-residue values: residues, chains, segments, models and structures are vectors of atoms, so sum(f, residue) (or mean(f, residue), with Statistics) computes the value of a residue from any atomic property, and eachresidue iterates over the residues;
  • sequences: getseq, oneletter;
  • geometry: center_of_mass, positions, distance;
  • solvent accessible surface areas: sasa_particles and sasa.

Compute first, then plot

Computation and plotting are separate. A function computes the result and returns it as a custom type, which carries everything needed to plot it, and can be used without any plotting package. The plot is a method, for that type, of a function of the plotting package (heatmap, plot, scatter, ... of Plots):

ComputationResultPlot
contact_mapContactMapheatmap(map)
RamachandranRamachandranscatter(ram)
hammer_aitoff_mapHammerAitoffMapheatmap(map)
helical_wheelHelicalWheelplot(wheel)

The result types have a show method, and fields with descriptive names.

The plotting methods are defined in the Plotting extension (in the ext directory), which is loaded with using Plots. Plots is the default plotting package. Another plotting package (for example, CairoMakie) can be used when it is better suited for a feature: it is then a weak dependency of the package, with its own package extension, loaded only when the user loads that package. A new extension, and the weak dependency it requires, must be clearly stated in the description of the pull request.

Plotting functions return the plot, and do not save it: users save figures with savefig (so there are no output or outfile keywords).

One quantity per function

If two quantities are computed, prefer two functions, each returning one quantity, to a function returning a tuple. For example, hydrophobic_moment returns the moment (a vector) and mean_hydrophobicity returns a number.

Periodic boundary conditions

Functions that support periodic boundary conditions have a unitcell keyword argument, which is false (default, no periodic boundary conditions), true (use the unit cell of the Structure), or a UnitCell. See Structures and unit cells.

Names

  • Function names are descriptive, in snake_case, and avoid abbreviations: hammer_aitoff_projection, not hammer; secondary_structure_diagram, not ss. Names are part of the public interface, and are hard to change after a release.
  • Type names are in CamelCase (HammerAitoffMap).
  • Export only the functions and types that users call. Helper functions are internal, and their names start with _ (e.g. _binned_statistic_2d). Constants and data tables (e.g. hydrophobicity scales) are internal, and their sources are cited in the documentation.

Code organization

  • Source files go in src (or in a subdirectory of src), with the export statements at the top of the file. They are included in src/PDBTools.jl, in the section they belong to, before the precompilation workload.
  • Plotting code goes in the ext directory, and is included in ext/Plotting.jl.
  • Dependencies: avoid new dependencies. A heavy dependency, needed by a single feature, should be a weak dependency, with a package extension. New dependencies and extensions must be clearly stated in the description of the pull request.

Tests

  • Tests are @testitems, in the same file as the code they test (plotting tests in the files of the ext directory). They are run with ]test, or individually in VS Code.
  • Test the results (with known values, or with properties that must hold), and also the errors, with @test_throws, for invalid inputs.
  • Test files are obtained with PDBTools.test_file("name"), after using LazyArtifacts. The test files are lazy artifacts, from the MolSimTestFiles repository, and are not part of the package. If a new test file is needed, mention it in the pull request: it will be added to a new release of MolSimTestFiles.
  • The quality tests of Aqua.jl must pass.

Documentation

  • Every exported function and type has a docstring, with the signature, the description of the arguments and keyword arguments, the return value, and an example. The examples start with using PDBTools, LazyArtifacts, and use PDBTools.test_file. The documentation build checks that every public name is in the manual.
  • New features are described in a page of docs/src, which must be added to the pages of docs/make.jl (otherwise it is not reachable in the documentation). The page explains what the feature is for, and contains the docstrings in a @docs block.
  • Examples in the pages are @example blocks, which are run when the documentation is built, such that the results and figures are shown and the examples are known to work. Use $```julia$ blocks only for code that cannot be run (e.g. code that needs data that is not available).
  • Equations are written in $```math$ blocks, or inline as ``\alpha``.
  • The documentation is built with julia --project=docs docs/make.jl. For pull requests from branches of this repository, a preview is deployed to https://m3g.github.io/PDBTools.jl/previews/PR<number>/. For pull requests from forks, the documentation is built (and checked), but not deployed: build it locally to see it.

Changelog

Every pull request adds an entry to CHANGELOG.md (this is checked in the CI), in the section of the version under development (at the top), below its header line. The entries start with a badge, which classifies the change:

- ![FEATURE][badge-feature] `new_function` computes ...

The badges are FEATURE, ENHANCEMENT, BUGFIX, BREAKING, DEPRECATION, EXPERIMENTAL and INFO. The entry describes the change for users: what can be done, with which functions.

New features are released in a new minor version (e.g. 4.3.0), and bug fixes in a new patch version (e.g. 4.2.1). Breaking changes require a new major version, and are avoided.
